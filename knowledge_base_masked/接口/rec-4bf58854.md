# 【迭代N】AI技能运行日志「触发方式」「触发用户」筛选不生效，选中任一条件结果恒为0条

## 现象
【测试环境】

admin/#/ai-skill-runtime-log
页面定位：AI平台→AI技能→运行日志→触发方式/触发用户 筛选

【测试分支】

develop

【测试账号】

<已脱敏账号凭据>

【前置条件】开发环境已部署 AI 运行日志功能（2026-09-23 版本），技能日志共 830 条。

【测试步骤】

进入「AI平台 → AI技能 → 运行日志」。

「触发方式」下拉选任一项（如「AI助理对话触发」/「表单模块触发」/「API触发」），点「搜索」。

「触发用户」填列表上真实存在的用户（如「李启银」），点「搜索」。

对照同一条件在「大模型/工具/助理」日志页的结果。

用接口复现（参数名由前端实际请求抓取得到）：

POST /api/api/ai/agent/logs/query

A 基准  {"logType":"SKILL","traceId":"6937e53dcb2541d791c4e3b4072bc961"}
B 加用户 {"logType":"SKILL","traceId":"6937e53dcb2541d791c4e3b4072bc961","triggerUser":"李启银"}
C 加方式 {"logType":"SKILL","traceId":"6937e53dcb2541d791c4e3b4072bc961","triggerMode":"AGENT_CHAT"}
对照   {"logType":"MODEL","traceId":"4640a6df37724a45...","triggerMode":"AGENT_CHAT"}

【预期结果】筛选条件应缩小结果集，且不能把满足条件的记录排除掉。

【实际结果】

技能日志页「触发方式」「触发用户」筛选完全不生效，结果恒为空。 同一条记录加上筛选条件后从 1 条变成 0 条：

A 基准（只有 traceId）                       → total=1
该记录：SKILL 触发用户=李启银 触发方式=AGENT_CHAT(AI助理对话触发) 触发位置=LUI
B 再加 triggerUser=李启银                     → total=0   ← 应为 1
B2 再加 triggerUser=<内部标识>（账号）            → total=0   ← 应为 1
C 再加 triggerMode=AGENT_CHAT                → total=0   ← 应为 1
D 仅 triggerUser=李启银                       → total=0   ← 列表中可见多条「李启银」
E 仅 triggerMode=AGENT_CHAT                  → total=0

把该记录接口返回的字段值原样回填仍为 0（排除传参错误的可能）：

triggerUser = 该记录 user.name "李启银"        → total=0
triggerUser = 该记录 user.id   "5c72c7e8..."   → total=0
triggerMode = 该记录 mode.code "AGENT_CHAT"    → total=0

页面层同样：技能日志共 830 条，选任一「触发方式」后点搜索，结果由 830 条直接变为 0 条，请求体为  {"logType":"SKILL","pageNo":1,"pageSize":20,"triggerMode":"FORM_CONTROLLER"} （参数已正确发出，是后端未命中）。

对照：同样两个筛选条件在其它日志页正常

MODEL  traceId 基准 10 条 → 加 triggerMode   仍 10 条 ✅
MODEL  traceId 基准 10 条 → 加 triggerUser   仍 10 条 ✅
TOOL   traceId 基准  4 条 → 加 triggerMode   仍  4 条 ✅
AGENT  traceId 基准  2 条 → 加 triggerUser   仍  2 条 ✅
ALL    仅 triggerUser=李启银 → 2983 条 ✅

影响 ：技能日志是「表单调用AI、AI技能触发」等场景的主要排查入口，这两个条件又是需求 3.3.2 明确要求的能力。用户按触发方式/触发用户筛选时得到「暂无数据」，会误判为「该场景没有产生日志」。且列表当前把所有 830 条都显示为「AI助理对话触发」，用户无从判断。

## 根因
缺失的 packages/<内部标识>-ai/ai-platform/components/ai-runtime-log/generic/presets/common.ts（createResourceLogFetchData / runtimeCommonFilterProperties / runtimeCommonColumns）才是条件拼装与字段映射的位置，本次未提供；已提供的 skill.ts 只声明 properties/columns/fetchData 且与 MODEL/TOOL/AGENT 共用同一套 common 构造器，runtime-log-page.vue、runtime-log-table.vue、skill-table-panel.vue 均不参与查询条件拼装。缺陷请求体已证明前端按 {"logType":"SKILL","triggerMode":"FORM_CONTROLLER"} 正确发出参数，而同一套条件在 MODEL/TOOL/AGENT 全部命中、仅 SKILL 恒为 0，属 SKILL 日志查询服务端字段/条件未生效（或 SKILL 记录里触发方式/触发用户存储字段与查询字段不一致，导致列表侧也只能取到默认值 AGENT_CHAT）。

## 说明
现有证据不足以在前端给出确定的最小改动：如果是 common.ts 中 SKILL 分支把 triggerUser/triggerMode 映射成了错误字段名或直接丢弃，需要在 common.ts 里改映射；但从抓包看参数名、值（用户姓名/账号、AGENT_CHAT/FORM_CONTROLLER）已原样发出且其它 logType 正常，说明前端链路无误，问题落在 /api/api/ai/agent/logs/query 对 logType=SKILL 的条件匹配与字段存储上。因此不修改任何前端文件可避免把后端缺陷掩盖成前端脏补丁；建议补充 common.ts 与后端 SKILL 日志查询/表结构后，再决定是否需要前端降级处理。
