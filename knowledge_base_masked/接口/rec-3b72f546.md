# 【迭代N】AI运行日志显示时间比实际时间早8小时

## 现象
【测试环境】

admin/#/ai-skill-runtime-log
页面定位：AI平台→AI技能→运行日志

【测试分支】

develop

【测试账号】

<已脱敏账号凭据>

【前置条件】

开发环境已部署 AI 运行日志功能，库中已有技能日志数据。

【测试步骤】

进入「AI平台 → AI技能」，点击右上角「运行日志」。

记录列表中第 2、3 行的「触发时间」。

用这两行的 Trace ID 查询数据库 h_executionnodelog 表的 startTime。

点任一行「查看详情」，查看详情页的「开始时间」。

【预期结果】

列表「触发时间」与详情「开始时间」应等于该次执行的真实发生时间。

【实际结果】

四个日志页的列表「触发时间」及所有详情页「开始时间/结束时间」均比真实时间早 8 小时。

Trace 80e7bb17bc1747a7a6012ad33951d72b：页面显示 2026-09-23 04:58:55，库 startTime 为 2026-09-22 20:58:55。

Trace ae5dec68d8b440ffaea35facad47427a：页面显示 2026-09-23 04:49:58，库为 2026-09-22 20:49:58。

详情页「开始时间 2026-09-23 04:58:55」，接口返回  "startTime":"2026-09-22T20:58:55Z" 。

库中存的是本地时间：服务器时间 2026-09-22 21:29:29 与 MySQL NOW() 完全一致，最新一条日志 startTime 为 21:29:03（若为 UTC 应约为 13:29）。接口给本地时间值直接加了  Z  后缀，前端按 UTC 解析后再转本地时区，造成二次 +8 小时。

受影响页面：技能日志、工具日志、大模型日志、统一日志四个列表，以及各日志详情页。

## 根因
提供的嫌疑文件中没有任何一个属于 AI 运行日志（admin/#/ai-skill-runtime-log）的列表或详情渲染代码——lui/pages/schedule/*、lui/mobile/pages/schedule/*、packages/<内部标识>-utils/src/full-calendar.ts 内既没有日志字段（startTime/endTime/executeTime）的格式化代码，也没有出现给无时区的时间串加 Z 的逻辑，因此无法在这批文件里定位到产生 -8 小时的具体行。缺陷根因在接口与页面之间：h_executionnodelog.startTime 存的是本地时间，接口序列化时误加了 Z 后缀（如 "2026-09-22T20:58:55Z"），页面再用 new Date()/moment() 按 UTC 解析、再按本地时区展示，导致二次 +8 小时。

## 说明
由于运行日志的列表/详情组件及其日期格式化工具未在嫌疑文件中给出，任何在此处的改动都会落到与缺陷无关的定时任务/日历代码上，属于猜测性修改，风险大于收益。正确的修法有两种，任选其一即可根除该现象：一是后端序列化 h_executionnodelog 的 startTime/endTime 时不要给本地时间加 Z（或直接返回 ISO 本地串）；二是前端在解析日志时间时把返回值当作本地时间处理，例如去掉末尾的 Z 再用 moment/严格解析（moment(value.replace(/Z$/, '')) 或改用 dayjs(value).format('YYYY-MM-DD HH:mm:ss') 前先做同样的处理），而不要用 new Date('...Z') 走 UTC 分支。影响面仅限日志时间的展示，不涉及数据写入。

## 预防措施
1) 接口契约中明确时间字段的时区语义（本地时间不带 Z，UTC 才带 Z），并在 API 文档与后端序列化基类中统一实现；2) 前端统一收口一个 parseLocalDateTime 工具函数，禁止业务代码直接 new Date(字符串) 解析后端时间；3) 为时间展示补充单测/联调用例，用固定样例（如 startTime=2026-09-22T20:58:55Z 期望展示 20:58:55）覆盖列表与详情；4) 部署环境统一时区并在联调 checklist 中加入“服务器时间与库 NOW() 一致性”验证。
